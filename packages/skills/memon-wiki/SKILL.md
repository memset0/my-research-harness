# Maintain the project explanation

Read `../PREFLIGHT.md` once and the relevant page's standing instructions.
Write for someone trying to understand the research: state the question,
what the evidence supports, what remains uncertain, and why the direction
changed. Revise the current explanation rather than appending activity logs.

Use `memon wiki --help` for IDs, creation, metadata and editing. Read
[references/page-kinds.md](references/page-kinds.md) when choosing a kind or
status, and [references/page-rules.md](references/page-rules.md) for maintenance.
Existing frontmatter and kind vocabularies remain supported; do not change
unrelated pages as a side effect of a research task.

Link claims to Experiment evidence, selected Variants or native artifacts.
The page can summarize the relevant numbers; it need not duplicate an entire
result table or copy one universal summary word for word. Look into original
artifacts when a question requires them. Distinguish measured facts, plausible
interpretations, untested ideas, invalid measurements and precision limits.
A retired experiment can still provide valid historical evidence.

## Choose the expression that helps the reader

Markdown, diagrams, charts and standalone HTML are all valid. Choose the form
that explains the question; do not constrain the agent to a mandatory component
or report template. A useful report can live directly in the Wiki. For a bundle
with HTML/assets, read [references/html-bundle.md](references/html-bundle.md).
Use `memon-components` only when its supported component syntax helps. A static
HTML view may be regenerated by a script; record the script when it aids reuse.
An always-live monitor requires a running service and an explicitly configured
connection, not a claim that a saved HTML file is live.

Update the Wiki when research understanding, route choice or an important
explanation changes. Routine execution status, commands and troubleshooting
stay with the experiment or native logs. Put independent technical details in
an experiment's `details/` directory when useful; keep its main comparative
evidence together. Do not create a second deliverable registry.

## Preserve meaning while reducing text

Replace obsolete main text with the current judgment. Keep consequential
historical turns briefly, using a collapsed Obsidian callout when appropriate:

```markdown
> [!DEPRECATED]- Previous interpretation
> Explain why this interpretation was replaced and link its original evidence.
```

Retirement, incorrect measurement, limited precision and a better subsequent
method require different explanations. Do not silently erase qualifications or
promote superseded evidence into current results. Use deletion only within the
user's authorization; historical citations must continue to work.

Follow each existing page's declared language. New pages use the user's stated
preference, otherwise English; preserve technical identifiers. When the user
sets standing maintenance rules, update the existing compact rules section.
Distinguish those instructions from an agent's proposed new policy; do not turn
every incident into a mandatory rule.

Verify changed links, relevant syntax and rendered HTML/interactive behavior.
There is no Git-based Wiki review layer, human-review checkbox gate, mandatory
feedback issue or per-Run Wiki update. Commit ordinary source changes according
to project instructions; do not invent a review ledger.
