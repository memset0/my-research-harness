## Why

memon currently couples the Web UI and cluster-local backend into the same deployment, so even a frontend-only change can require redeploying every experimental cluster. The project needs one centrally deployed Web entry point backed by independently deployed cluster services, allowing each side to evolve and roll out without unnecessary fleet-wide updates.

## What Changes

- Split memon into two independently deployable roles:
  - a single central Web service containing the frontend and a lightweight gateway for routing, aggregation, and cross-cluster presentation;
  - one backend service on each experimental cluster, responsible for that cluster's project directories, discovery, file access, events, and supported cluster-local operations.
- Deploy exactly one memon backend per experimental cluster, normally on that cluster's login or management Host—not one backend per GPU compute node. Agents operating inside the cluster use the cluster's existing mechanisms to reach individual GPU nodes when needed.
- Keep cluster-backend configuration close to today's deployment model: each backend declares the local project directories and cluster-local features it exposes.
- Give the central service a local configuration that declares which cluster backends it connects to, their identities, endpoints, credentials or connection references, and any routing metadata required to distinguish them.
- Keep the central configuration out of Git. Its comments serve as the Agent-maintained operations notebook describing how each cluster is reached, installed, upgraded, restarted, or otherwise administered; machine-readable connection settings and operational guidance live together in that local file.
- Separate two paths that happen to originate from the central host:
  - the **runtime path**, where the central gateway reaches the versioned backend API associated with each local or remote Host and exposes those APIs through one aggregated central access surface;
  - the **operations path**, where an Agent follows the local configuration to SSH to cluster machines and install or update the versioned CLI + backend distribution.
- Model the deployment hierarchy as `Host -> Backend API -> Projects`. Every configured Host has one cluster-backend identity, and every discovered Project belongs to exactly one Host at a time.
- Let the central gateway query all configured Host backends, merge their project and status views, preserve Host ownership, and route Host-qualified reads and mutations back to the correct backend.
- Require the gateway to provide one stable central namespace even though the underlying backend APIs live on different cluster Hosts. Each Host entry selects one of two runtime transport modes:
  - **forwarded**: an external mechanism has already made the backend reachable, and the local configuration supplies the resulting center-local URL including its port;
  - **ssh**: the local configuration supplies the SSH target and remote backend endpoint/path information, and the central gateway establishes, monitors, reconnects, and tears down the tunnel itself.
- Normalize both transport modes into the same internal backend upstream so API aggregation, health/version checks, events, and terminal routing do not depend on how connectivity was established. Exact configuration fields and SSH tunnel mechanics are deferred to design.
- Replace name-only Project identity with a Host-qualified Project identity. Every Project carries its owning stable Host identifier, and the `(host, project)` pair—not the Project name alone—flows through core data structures, API contracts, URLs, cache/query keys, events, authorization scopes, and frontend state. Equal local Project names on different Hosts remain distinct, while one concrete Project belongs to exactly one Host.
- Allow the central Host to run a normal cluster-backend instance alongside the central Web/gateway. The default central deployment registers this local backend with the repository's mock Projects, so the same dashboard can show clearly Host-labelled mock data together with real Projects aggregated from remote Hosts.
- Keep mock data on the same backend API and routing path as real data rather than adding a frontend-only filesystem shortcut. This makes the default local backend a deployment smoke test for the same contract used by remote backends.
- Make remote ttyd forwarding an explicit **central-gateway responsibility** rather than treating ttyd as an ordinary JSON API. The central gateway owns Host routing, forwarding/tunnel state, and relay of both ttyd HTTP traffic and WebSocket upgrades by `Host + session`; the selected cluster backend is limited to owning the local ttyd process, port, and lifecycle registry.
- Keep ttyd bound to the cluster Host's local security boundary and do not expose each dynamic ttyd port directly to the public network. The central service reaches it through the Host backend/transport and presents one authenticated, Host-qualified terminal URL to the browser.
- Require terminal forwarding state to follow terminal lifecycle: start registers a Host-qualified route, attach reuses it, disconnect/reconnect does not silently target another Host, and kill or stale-process cleanup removes it. Exact tunnel management, path rewriting, backpressure, and reconnection mechanics are deferred to design.
- Introduce a project release version that is independent from `FS_CONVENTION_VERSION` and other on-disk schema versions. Both central and cluster deployments report this version, and the central gateway determines backend compatibility before using a backend.
- Define two release compatibility classes:
  - a **patch-level update** keeps the existing cluster-backend contract compatible, so only the central deployment needs to be updated and cluster machines do not need reinstalling;
  - a **minor-level update** introduces a new cluster-backend version and starts a fleet rollout, while the central service retains compatibility with exactly the immediately preceding Minor.
- During a Minor rollout, a central service at Minor `N` accepts cluster backends at `N` and `N-1`. An `N-1` backend remains usable and is shown as `update available`; anything older is blocked as `upgrade required` rather than being misreported as a network failure.
- For a Minor rollout, update the central deployment first. After development and the central update are complete, an explicit user request can direct the center-side Agent to read the Git-ignored operations configuration, visit every non-central cluster over SSH, and deploy the matching cluster distribution. This is an Agent-driven, user-triggered rollout, not an unattended background auto-update.
- Add a native local update operation to the memon CLI for the Agent to invoke on each cluster. It brings that Host's memon Git checkout to the target revision corresponding to the central release, runs the canonical installation step, restarts the supervised backend daemon, and verifies the resulting version and health.
- Pin a rollout to the central deployment's target version/revision instead of resolving an independently moving `latest` on every Host. Repository synchronization must fail safely rather than discard an unexpected dirty or divergent cluster checkout; exact Git and rollback behavior is deferred to design.
- Preserve independent release value: a frontend-only patch must require redeploying only the central service, while backend-required releases support a controlled cluster-by-cluster rollout after the central update.
- Provide a user-level process-management model for each cluster backend that does not require root access or registration as a system service. The primary mode runs a persistent lightweight supervisor/watchdog that owns and monitors the backend API worker, restarts it after unexpected exit with bounded backoff, and survives the originating SSH shell.
- Add first-class native daemon management to the memon CLI, including lifecycle inspection and start, stop, and restart operations. This is a supported product surface—not an environment-specific shell script or systemd wrapper—and backend-required upgrades use it so the installed distribution and the running daemon cannot silently remain on different versions.
- Support multiple process modes without changing the backend API contract: supervised background mode is the normal cluster deployment; foreground mode supports debugging; externally supervised mode permits systemd or another site-provided service manager where available.
- Require unambiguous daemon ownership and observable state. Duplicate starts, stale process metadata, crash loops, startup failures, and intentional stops must be distinguishable rather than producing multiple competing backend API processes.
- Do not provide cross-reboot automatic backend recovery in this change. The rootless supervisor survives the originating SSH shell and restarts a crashed API worker, but a cluster Host reboot leaves the backend stopped until a center-side Agent follows the local operations configuration, SSHes to that Host, and invokes the native CLI start operation.
- Treat the network path as an operational prerequisite. The operator may provide direct routing, SSH-based access, a private overlay, or another mechanism; this proposal defines the memon service boundary and configuration, not how the underlying network is built.
- Keep all environment-specific SSH topology, hostnames, jump-host rules, commands, credentials, and operational cautions out of OpenSpec and the tracked codebase. Those details belong exclusively to the center-local, Git-ignored configuration.
- Isolate failures by Host: an unreachable backend leaves its configured Host visible with an explicit `offline` state without taking down the central UI or other reachable Hosts. Do not add offline or last-known-data caching in this change; Project/experiment/run payloads from that Host are unavailable until its backend reconnects.
- Remain provider-neutral and keep deployment artifacts and specifications free of environment-specific provider identities.
- Treat this as a clean architecture redesign. The discarded `add-hub-node-split` proposal and implementation direction—including its Hub/Node topology, node-initiated dialing, and WebSocket RPC transport—provide no design or compatibility constraints for this change.
- **BREAKING**: separate the current co-located Web/backend runtime, release artifacts, configuration, and deployment lifecycle into central and cluster roles.
- **BREAKING**: cluster-local assumptions in URLs, APIs, caches, events, and operational features become explicitly cluster-scoped.

## Capabilities

### New Capabilities

- `split-service-deployment`: Independently buildable and deployable central-Web and cluster-backend roles, their configuration ownership, lifecycle, rollout, rollback, and compatibility expectations.
- `cluster-backend-api`: The authenticated, versioned contract through which the central gateway discovers Host-backend capabilities and performs Host-scoped reads, writes, events, and supported operational actions.
- `central-cluster-registry`: The Git-ignored local central configuration that names cluster Hosts and their single backends, selects `forwarded` or gateway-managed `ssh` connectivity, supplies connection/routing data, and permits Agent-maintained operational notes in comments without turning the repository into the source of machine-specific secrets or topology.
- `backend-tunnel-management`: Central-gateway ownership of SSH tunnel establishment, health monitoring, reconnection, shutdown, and normalization alongside externally pre-forwarded local backend URLs.
- `central-mock-backend`: The default local backend registration on the central Host that exposes repository mock Projects through the same versioned API and Host-qualified dashboard path as remote real Projects.
- `host-qualified-project-identity`: The mandatory `(host, project)` identity carried consistently through core models, APIs, routes, events, cache keys, authorization scopes, and UI, with exactly one owning Host per Project.
- `host-availability`: Live per-Host connectivity and compatibility states, including explicit `offline`, `update available`, and `upgrade required` presentation without offline data caching.
- `release-compatibility`: Project-level release versions, patch-compatible versus backend-required updates, version reporting and negotiation, the `update available`/`upgrade required` states, an exact one-Minor compatibility window, and the central-first staged rollout contract.
- `cluster-backend-distribution`: The versioned CLI + backend installable deployed to each experimental cluster and the install/update boundary used by center-originated SSH operations.
- `cluster-backend-update`: A native local memon CLI operation that safely synchronizes the cluster checkout to a pinned target revision, runs installation, restarts the daemon, verifies version/health, and returns an Agent-readable result.
- `cluster-backend-daemon`: Rootless backend lifecycle exposed as a first-class native memon CLI feature, including supervised background/foreground/external modes, watchdog behavior, state and version reporting, failure backoff, upgrade-safe restart semantics, and the explicit absence of automatic cross-reboot recovery.
- `remote-terminal-forwarding`: The central gateway's Host- and session-qualified forwarding of ttyd HTTP and WebSocket traffic, including tunnel/route ownership, lifecycle coordination, failure isolation, and the rule that cluster-local dynamic ttyd ports remain non-public.

### Modified Capabilities

- `web-dashboard`: The central dashboard aggregates Projects from all configured Host backends, visibly identifies each Project's owning Host, keeps navigation and mutations scoped to that Host, and presents offline Hosts without stale Project data.
- `memon-cli`: Serving the central Web role and installing, updating, or managing a cluster-backend daemon become explicit deployment paths; native update and daemon lifecycle commands are supported CLI features while ordinary project commands continue to work locally on experimental clusters.
- `live-updates`: Backend events carry Host-qualified Project identity across the service boundary and are merged by the central gateway without requiring the frontend deployment to own cluster-local polling.
- `tmux-session-management`: Session discovery and management are cluster-scoped and routed to the selected cluster backend.
- `browser-terminal`: Terminal start, attach, proxy, and lifecycle behavior use a Host-qualified central URL while the terminal process and dynamic port remain owned by the selected cluster backend.
- `auth-system`: Human access and viewer scopes use Host-qualified Project identity at the central service, while central-to-backend service authentication and remote-operation authorization form a separate trust boundary.

## Impact

- **Repository/package boundaries**: frontend, central gateway, shared protocol/types, and cluster backend need release boundaries that permit independent builds and deployment.
- **Configuration**: the central host gains a Git-ignored local cluster registry and operations notes, with a default local-backend entry for repository mock Projects; every cluster retains a local backend configuration for project roots and local capabilities. The exact filename and machine-readable schema are deferred to design; real SSH and operations content is explicitly not an OpenSpec or codebase artifact.
- **Versioning**: project release compatibility becomes a first-class contract separate from filesystem/schema migration. Central Minor `N` supports backend Minors `N` and `N-1`; the numeric format and major-version policy remain design decisions.
- **Core identity and APIs**: every surface that currently treats `project` or `projectName` as globally sufficient must carry a stable Host identifier as well. This includes shared types, URL generation, route parameters, request/response payloads, query keys, event payloads, viewer/share scopes, terminal targets, and collision validation.
- **Backend/runtime**: one API backend per experimental cluster owns project discovery, indexing, filesystem access, polling, event production, tmux processes, ttyd processes, and the local session-to-port registry. Individual GPU compute nodes do not run this service. The API worker gains a rootless supervisor/watchdog and CLI lifecycle boundary independent of systemd availability.
- **Frontend/gateway**: Host-qualified Project identity, Host labels/grouping/filtering, multi-backend API aggregation, routing, event fan-in, compatibility reporting, explicit offline states without cached Host data, and ownership of the authenticated HTTP/WebSocket terminal relay all move to the central deployment.
- **Security**: the central service holds backend connection credentials or references; both human-to-central and central-to-backend boundaries require explicit authentication, authorization, secret handling, and path safety.
- **Operations**: patch-compatible releases affect only the central deployment. Backend-required releases update the center first, then an explicitly instructed Agent rolls the pinned revision through clusters over SSH using the native CLI update operation and reports per-Host results. After a Host reboot, the same Agent-driven path starts its daemon manually. The central gateway owns configured runtime SSH tunnels, while Agents maintain actual Host details and operating procedures only in the local central configuration.
- **Discarded predecessor**: no artifacts, transport decisions, or migration requirements from `add-hub-node-split` are carried forward. Later specs and design start from the topology defined by this proposal.
